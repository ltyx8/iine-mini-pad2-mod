# 良值 L1254（复古迷你手柄2）V1 协议实测与改键说明

> 全部内容来自真机抓包，不是从 APK 推断的。设备 `F8:B4:9A:CC:71:CE`，广播名 `IINE_mouse`，
> 固件自报 `mode_name=ig05, version=4096 (0x1000)`。
> 抓包工具：`ble_scan.py`（扫描）、`winrt_link.py`（WinRT 直连）、`web/keymap.html`（网页）。

---

## 1. 为什么你的手柄跟之前那套 V2 协议对不上

App 里两套命令族并存，靠产品表的 `platform` 字段分流：

| | V1 = `joymi` | V2 = `joymi-v2` |
|---|---|---|
| 命令 | `get_info` / `get_kb` / `get_mouse` / `get_screen` / `get_mt` / `get_cs` / `get_sleep` | `g_devinfo` / `g_rkey` / `s_key_test` … |
| 响应 | 统一 `ret_` 前缀（`get_info` → `ret_info`） | 与请求同名 |
| 实时按键 | **没有**（App 读 Android `InputDevice`） | `g_kt` 主动上报 |
| 你的 L1254 | ✅ 就是这套 | ✗ 完全不应答 |

实测：发 `g_kt` 等 6 秒，一个字节都不回。**V1 机型只能走系统 HID 读按键状态。**

## 2. 传输层（两套通用）

```
服务 0000AE40  写特征 AE41 (props=0x04, 无响应写)  通知特征 AE42 (props=0x10)
帧    B4 | LEN(本帧总长) | SEQ | CC | msgpack payload
SEQ   bit7=1 表示新消息首片，低 7 位 = 剩余片数，最后一片必须为 1
分片  每片 payload = MTU-7；无 CRC、无 ACK
```

一整条 376 字节的 `get_kb` 响应会拆成 **9 帧**到达，收端必须按 SEQ 累加。

### 2.1 实测连接参数（adb logcat，2026-10-29）

```
Requesting MTU of 517  →  MTU changed successfully to: 64, limited to: 48
JoyMi: Using MTU=48, max characteristic write limit=45   → 每片 payload 41 字节
```

App 实际把 MTU 谈成 64、自己压到 48，单次写上限 45 字节（含 4 字节帧头），
所以**每片携带 41 字节 msgpack**。我们网页的 `buildFrames` 默认用 20，只是保守，
功能一样、帧数多一倍；要提速可以把 chunk 调到 41。

### 3.1 `get_info`

```
请求  {cmd:"get_info", key:"all"}
响应  {cmd:"ret_info", mode_name:"ig05", version:4096}
```

`version=4096` 即 `0x1000`，是 BCD 风格的版本字。

### 3.2 `get_kb`（读键盘映射）

```jsonc
{ "cmd":"ret_kb", "map":[
    { "key":0, "fn":0, "kb":<ext0 04 00 01> },
    { "key":1, "fn":0, "kb":<ext0 05 00 03> },
    … 共 17 条
]}
```

`kb` 不是普通数组，是 **msgpack ext type 0，长度 3**：

```
C7 03 00 <键码> <修饰键> <序号>
```

- **键码** = HID Keyboard Usage（`0x04`='A'，`0x05`='B'，`0x28`=Enter，`0x4F`=Right…）
- **修饰键** = HID modifier 位域（1=LCtrl, 2=LShift, 4=LAlt, 8=LWin）
- **序号** = 固件自己维护的链表值，回读时恰好等于下一条的 `key`；**写入时官方 App 固定填 0**，固件收到会重算

> 标准 msgpack 库会把这个字段解成 `ExtType`，必须单独处理，否则整条响应解不出来。

### 3.3 `set_kb`（写键盘映射）

每个字段值都是**手写字节**（App 用 `addPayload()` 直接塞原始字节，不是 pack 出来的值）：

```
82                          map(2)
  A3 "cmd"  A6 "set_kb"
  A3 "map"  91              array(1)
    83                      map(3)
      A3 "key"  CC <key>    ← 显式 uint8
      A2 "fn"   CC <fn>
      A2 "kb"   C7 03 00 <键码> <修饰键> <00>
```

关键点：

1. `key` / `fn` 必须写成 `CC xx`（显式 uint8），不能依赖 fixint 自动压缩
2. `kb` 的第 3 字节写 `0`，别把回读值原样写回
3. **必须全量写**：`map` 数组长度 = 当前全部槽位数。只发一条会把其余槽位清空
4. 不回包，写完 sleep 400–600ms 再 `get_kb` 回读校验

### 3.4 `get_gp` / `set_gp`（手柄键互换）

「手柄」栏不是只读的 —— 它把**手柄上的某个物理键换成手柄上的另一个键**。
命令名由 `"get_"/"set_"` 拼上机型分支得到：`JoyMiGamepadSettingsViewModel` 里
`pid == "2001" ? "gp" : "xinput"`，所以 L1254 走 **`get_gp` / `set_gp`**。

```jsonc
请求  {cmd:"get_gp", key:"all"}
响应  {cmd:"ret_gp", map:[ {key:8, gp:7}, {key:9, gp:8, times:0}, … ]}
```

三个字段：

| 字段 | 含义 |
|---|---|
| `key` | 物理键槽位（与 `get_kb` 的 key 同一套编号） |
| `gp` | 映射目标 —— **也是槽位号，不是 GamepadKey.rawValue**。值域就是下面那 17 个 |
| `times` | 连发次数，回读总有 `0`，但写入时 App 不写这个字段 |

写入是**手写字节**（下面这段是从 logcat 抓到的官方 App 真实 payload，不是推断）：

```
82 a3"cmd" a6"set_gp" a3"map" dc 00 11
   82 a3"key" CC <key> a2"gp" CC <gp>        ← map(2)，key/gp 都是 0xCC(uint8)
```

两个坑：

1. **是 `0xCC`，不是 `0xD0`。** smali 里写的是 `const/16 v5, -0x34`，-0x34 = -52 → `0xCC`。
   一开始算成 `0xD0`，写下去固件毫无反应、回读一字不变。
2. **App 不写 `times`**（就 10 字节一条）。回读出来的 `times:0` 不要照抄回去。

另外**必须全量 17 条**：只发 1 条时固件直接忽略（回读不变，不是清空）。

机型相关的可选目标集合（`JoyMiProductRegistry` + `JoyMiProductSpec.gamepadKeys(version)`）：

```
1000_2001  base      = [0,1,3,4,6,7,8,9,16,17,18,19]
           固件 ≥ 0x800 追加 = [10,11,12,15,23]      ← 你的 0x1000 属于这一档
           合并去重排序 = [0,1,3,4,6,7,8,9,10,11,12,15,16,17,18,19,23]
```

这 17 个值正好就是 `get_kb` 返回的 17 条 key —— 两套映射共用同一套槽位号，
所以「键互换」的可选目标就是这 17 个键本身，没有别的。

### 真机实测（2026-10-29，`IINE_mouse` 鼠标模式）

| 动作 | 结果 |
|---|---|
| `get_info` `key:"all"` | ✅ `ret_info mode_name=ig05 version=0x1000` |
| `get_kb` `key:"all"` | ✅ `ret_kb`，17 条 |
| `get_mouse` `key:"all"` | ✅ `ret_mouse`，17 条（字段含义见下） |
| `get_gp` `key:"all"`（出厂状态） | ⚠️ `ret_gp`，**`map: []` 空表** |
| `get_xinput` `key:"all"` | ❌ 超时（说明这台确实走 `gp` 分支，不是 `xinput`） |
| 用 `0xD0` 编码 `set_gp` → 回读 | ❌ 无效（字节错） |
| 官方 App 改一次键并点「应用」→ 回读 `get_gp` | ✅ **17 条全出来了** |

**关键结论：出厂时这张表是空的，官方 App 点过一次「应用」之后固件才建立并返回它。**
表建起来之后，用 `0xCC` 编码全量写就能生效：

```
把 key=15（右圆 CAP）改成 L  → 写入 → 回读 key=15 gp=6   ✅
再把 key=15 改回 15          → 写入 → 回读 key=15 gp=15  ✅
```

`times` 字段实测回读恒为 `0`（不是 null），但 App 写入时不带它，所以别照抄。

### 槽位 12 / 15 = 截图 / HOME（以手柄实物为准）

**底部两个圆键：左 = 截图（CAPTURE），右 = HOME。** 与手柄本体印刷的
「◄ CAPTURE」「◄ HOME」一致。上排两个：左 = −，右 = +。

| 槽位 | 实物按键 | 本体印刷 | **App 主页面显示** |
|---|---|---|---|
| 12 | 截图 CAP | ◄ CAPTURE | ⌂ 房子（**错的**） |
| 15 | HOME | ◄ HOME | □ 方框（**错的**） |

App 有两处数据打架：手柄栏主页面是「左房子右截图」，改键弹窗的示意图却是「左方框右房子」
（后者与实物一致）。`gamepad_key_location.json` 里 95(截图) 在左、17(Home) 在右 —— 也是对的。
所以错的是 App 主页面的两个图标，网页按实物走，不要照 App 主页面抄。

### 3.5 `get_mouse` / `set_mouse`（鼠标栏）

```jsonc
请求  {cmd:"get_mouse", key:"all"}
响应  {cmd:"ret_mouse", map:[{key:0, but:1, w:0, x:0, y:0}, …]}    // 17 条
```

| 字段 | 含义 |
|---|---|
| `but` | 按键位：1 = 左键，2 = 右键，0 = 无 |
| `w` | 滚轮量：-1 = 上，+1 = 下，0 = 无 |
| `x` | 水平移动，带符号；**绝对值 = App 里「鼠标移动距离」那个滑块** |
| `y` | 垂直移动，带符号，同上 |

App 的「鼠标移动距离」滑块默认 2、最大 48（实测点最右是 48），写入时直接落到 `x`/`y` 的绝对值上。

**写入格式**（2026-10-29 `adb logcat -s JoyMiManager` 抓到的官方报文）：

```
82 a3"cmd" a9"set_mouse" a3"map" dc 00 11          ← map(2)，map 数组 17 条
   85 a3"key" CC <u8>                             ← 85 = map(5)
      a3"but" CC <u8>
      a1"w"   D1 <i16>
      a1"x"   D1 <i16>
      a1"y"   D1 <i16>
```

注意 **`key`/`but` 是 uint8（0xCC），`w`/`x`/`y` 是 int16 大端（0xD1）** —— 四种字段两种编码，
照抄 `set_kb` 的 `0xCC` 会把 int16 字段写坏。必须全量 17 条。

出厂 8 条非零（初始化后实测）：

```jsonc
{key:0,  but:1, w:0,  x:0,  y:0}    → 左键
{key:1,  but:2, w:0,  x:0,  y:0}    → 右键
{key:3,  but:0, w:-1, x:0,  y:0}    → 滚轮上
{key:4,  but:0, w:1,  x:0,  y:0}    → 滚轮下
{key:16, but:0, w:0,  x:0,  y:-2}   → 上移（十字上）
{key:17, but:0, w:0,  x:0,  y:2}    → 下移（十字下）
{key:18, but:0, w:0,  x:-2, y:0}    → 左移（十字左）
{key:19, but:0, w:0,  x:2,  y:0}    → 右移（十字右）
```

其余 9 条全 0（未映射）。每格 17 条，与 `get_kb` 的槽位一一对应。

> **⚠ 这台手柄出厂时鼠标方向是歪的**：初始化之前读到的是 16=x-2(左移)、17=x+2(右移)、
> 18=y+2(下移)、19=y-2(上移)，即十字「上」出「左移」。点一次「初始化手柄」之后才变正
> （16 上 / 17 下 / 18 左 / 19 右）。如果用户抱怨鼠标模式方向错乱，先让他初始化一次。

### 3.6 `get_cs` / `set_cs`（媒体键栏）

```jsonc
请求  {cmd:"get_cs", key:"all"}
响应  {cmd:"ret_cs", map:[{key:0, cs:205}, …]}    // 出厂 8 条
```

`cs` 是 **HID Consumer Page 的 usage**（不是键盘 usage）。出厂实测：

| 槽位 | 按键 | cs | 含义 |
|---|---|---|---|
| 0 | A | 205 (0xCD) | 播放/暂停 |
| 1 | B | 205 (0xCD) | 播放/暂停 |
| 3 | X | 183 (0xB7) | 停止 |
| 4 | Y | 226 (0xE2) | 静音 |
| 16 | ▲ | 233 (0xE9) | 音量+ |
| 17 | ▼ | 234 (0xEA) | 音量- |
| 18 | ◀ | 182 (0xB6) | 上一首 |
| 19 | ▶ | 181 (0xB5) | 下一首 |

App 媒体键弹窗那 9 个选项对应的值：

```
静音 0xE2   音量+ 0xE9   音量- 0xEA
播放/暂停 0xCD   上一首 0xB6   下一首 0xB5
亮度+ 0x6F   亮度- 0x70   睡眠 0x32
```

（出厂 X=0xB7「停止」在弹窗里没有对应项，但 `get_cs` 会返回它，网页要能显示。）

**写入格式**（实抓）：

```
82 a3"cmd" a6"set_cs" a3"map" dc 00 11     ← map(2)，17 条
   82 a3"key" CD <u16>                     ← 82 = map(2)
      a2"cs"  CD <u16>
```

`key` 和 `cs` **两个都是 uint16（0xCD）**，和 `set_kb` 的 uint8 又不一样。必须全量 17 条。

### 3.7 `get_sleep` / `set_sleep` / `set_restore`（其他栏）

```jsonc
请求  {cmd:"get_sleep", key:"all"}
响应  {cmd:"ret_sleep", map:[{discon:5, con:10}]}
```

`discon` / `con` = 无操作关机时间（分钟），**0 = 永不**。出厂实测是 `discon:5, con:10`（初始化后），
用户改过则为两值相同。App 的滑块范围 1–240 分钟，最右一档单独显示「永不」= 0。

**写入格式**（实抓）：

```
82 a3"cmd" a9"set_sleep" a3"map" 91 82 a6"discon" CC <u8> a3"con" CC <u8>
                              ↑ fixarray(1)  ↑ map(2)
```

map 里就一条，`discon` 和 `con` 同时设成滑块值，都是 uint8。

**初始化手柄**（`set_restore`）：纯命令、无参数、**无回包**：

```
b4 15 81 cc 81 a3"cmd" ab"set_restore"
```

实测效果：`get_kb` 全部回到出厂 17 条、`get_gp` 变空表、`get_mouse` 十字方向被修正、
`get_cs` 不变、`get_sleep` 回到 `5/10`。App 点完会退回「配置管理」页重新读配置。

**② 连上后只发一条命令**


| 顺序 | 请求 | 响应长度 | 条数 | 耗时 |
|---|---|---|---|---|
| 1 | `{cmd=get_gp, key=all}` | 17 B | **0**（`90` = empty array） | 53 ms |

## 6. 网页怎么用

```cmd
analysis\web\start.cmd     :: 双击，自动起本地服务并开浏览器
```

## 7. 已知限制

| 项 | 说明 |
|---|---|
| 改键只在**键盘模式**生效 | 当前 `IINE_mouse` 是鼠标模式，`get_kb` 的映射不会触发。要验证改键效果，切到 **配对键 + A（IINE-Keyboard）** |
| V1 没有实时按键流 | `g_kt` 静默无响应。网页的按键状态面板会自动切到 **Gamepad API**，需要手柄处于 Xinput 模式（配对键+左键），让 Windows 认出 xbox 手柄 |
| 同一时刻只能一个 GATT 客户端 | 网页连着时，Python 脚本连不上；反之亦然 |
| 写入不回包 | 只能靠回读确认；网页已经做成写完自动回读 |
| 出厂时 gp 表为空 | `get_gp` 回 `map:[]`，官方 App 点过一次「应用」之后表才建起来。网页读到空表时按 `SLOTS` 生成 17 条基线全量提交 |
| 出厂时鼠标方向是歪的 | 初始化前十字「上」输出「左移」。点一次「初始化手柄」后变正（16 上 / 17 下 / 18 左 / 19 右） |
| 触控（`set_mt` / `set_screen`） | 只读取，不做写入；网页已删掉该栏目（Windows 无触摸目标） |

## 10. 槽位号 ↔ 物理按键（实测确认）

固件不提供这个映射，只能用实验确定。

**方法**：在官方 App 里把 A 键改成 Z 并点「应用」→ 强制停止 App → 电脑读 `get_kb` → 找变化的槽位。

```
槽位 index=0、固件 key=0 从 040001 变成 1d0001   ← App 改的是 A 键
```

**结论：A 键 = 槽位 0。** 其余槽位按 App「键盘」栏的红标签逐条对齐：

| 槽位 | 出厂输出 | 物理按键 |
|---|---|---|
| 0 | A | A |
| 1 | B | B |
| 3 | X | X |
| 4 | Y | Y |
| 6 | L | L |
| 7 | R | R |
| 8 | 仅 LAlt（fn=4） | ZL |
| 9 | Enter | ZR |
| 10 | Backspace | − |
| 11 | Space | + |
| 12 | LShift | 截图 CAP（底边左圆键） |
| 15 | LCtrl | HOME（底边右圆键） |
| 16 | Up | ▲ |
| 17 | Down | ▼ |
| 18 | Left | ◀ |
| 19 | Right | ▶ |
| 23 | Delete | M1 |

> 踩过的坑：App 点「应用」按钮时，dump 出来的 bounds 是**文字**的边界，
> 按钮本体更宽。按文字中心点会点在按钮外，看起来"应用了"其实没写进设备。
> 正确判断方法是看「应用」按钮是否变灰（无待提交改动）。

### 连上之后网页读什么（和 App 完全对齐）

| 顺序 | 动作 | 依据 |
|---|---|---|
| 1 | `get_info`（带 `key:"all"`） | 既是协议识别，也拿到 `mode_name` / `version` |
| 2 | 读 GATT `0x180F / 0x2A19` 电量 | 和 App 一样走标准 Battery Service |
| 3 | `get_gp` → `get_kb` → `get_mouse` → `get_cs` → `get_sleep` | 顺序照抄 App 进「设备配置」时的实测序列（gp 最先），串行、每条等响应 |

> 过滤式扫描会返回 `NotFoundError`。这时页面会问要不要列全部设备，选「确定」即可。

### 方向键一键布局（手柄 / 鼠标两栏都有）

**基准姿态是「横着拿」**：手柄横握、十字键在左端、上键朝屏幕上方，此时四个键各归其位，
不需要任何改动。把整只手柄在屏幕平面内转 90° 就成竖握，但**转的方向有两个**，
十字键会分别落在手柄的上端或下端 —— 这两种是完全不同的映射，必须分开。

| 预设 | 旋转 | 上键(16) | 下键(17) | 左键(18) | 右键(19) |
|---|---|---|---|---|---|
| 横着拿 | 0° | 上 | 下 | 左 | 右 |
| 竖着拿 · 键在上 | 顺时针 90° | **右** | **左** | **上** | **下** |
| 竖着拿 · 键在下 | 逆时针 90° | **左** | **右** | **下** | **上** |

- **手柄栏**改的是 `set_gp` 的 `gp`（输出的槽位号）：`key16→gp19` 表示按物理上键输出"右"。
  `get_gp` 为空表时视为"没做过互换"，等价于横着拿，所以初次连上会高亮「横着拿」。
- **鼠标栏**改的是 `set_mouse` 里 `x`/`y` 的符号，步长沿用该键原本的距离（没设过按 2）。
- 快捷条只动这四个槽位，其余键一个都不碰；当前配置正好等于某个预设时，那个按钮会高亮。

> 早前版本把三个预设写成 0° / +90° / 180°，并让"竖着拿"等于不旋转 —— 是错的。
> 180° 那种握法（手柄整个倒过来）用户根本不用，真正要区分的是**竖握时十字键在上还是在下**。

## 12. 写入能力现状

**写入条数 = 传进去的列表长度**（`manuallyEncodeSetMousePayload` 里就是
`packArrayHeader(list.size())`），不是固定 17。所以：

- 初始化前读到 17 条 → 写 17 条（`dc 00 11`）
- 初始化后读到 8 条 → 写 8 条（`98`）
- 网页改了一个原本没映射的键 → 列表自然变成 9 条，写 9 条

网页的 `saveMouse` / `saveCs` 都是「读到的原样 + 草稿覆盖/追加」，和 App 行为一致。

| 项 | 状态 |
|---|---|
| 键盘 `set_kb` | ✅ 可用，全量写回 + 回读校验 |
| 手柄键互换 `set_gp` | ✅ 可用，全部 17 条、`key`/`gp` 都是 uint8，不写 `times` |
| 鼠标 `set_mouse` | ✅ 可用，17 条，`key`/`but` uint8 + `w`/`x`/`y` int16，距离落 `x`/`y` 绝对值 |
| 媒体键 `set_cs` | ✅ 可用，17 条，`key`/`cs` 都是 uint16 |
| 关机时间 `set_sleep` | ✅ 可用，单条 `{discon, con}` 都是 uint8，0 = 永不 |
| 初始化 `set_restore` | ✅ 可用，纯 `{cmd:"set_restore"}`，无参数无回包 |
| 触控 `set_mt` / `set_screen` | ⛔ 网页已删该栏目（Windows 没有触摸目标），只保留读取 |
| 槽位映射 | A=槽位0 是硬证据；其余按 App 红标签对齐。12=截图 / 15=HOME，10=− / 11=+。若某条对不上，改 `SLOTS` 表里那一行即可 |

## 13. 本地桥 `bridge.py`（为什么必须要有它）

**问题**：Windows 已经把手柄当鼠标连着的时候，它不再广播。Web Bluetooth 的
`navigator.bluetooth.requestDevice()` 用 name 过滤器扫不到它；就算改用
`acceptAllDevices` 列出来了，Chromium 也大概率抢不到 GATT 连接。

**做法**：`analysis/bridge.py` 用 PyWinRT 直接打开已配对设备的 AE40 服务，
同一个进程里再跑一个 HTTP 服务，网页改成走 HTTP —— 协议本身一个字没改，
仍然是网页拼 msgpack、后端原样收发帧。

```
python bridge.py --port 8848 --open
浏览器 http://127.0.0.1:8848/keymap.html
```

（`web/start.cmd` 已经改成调它，双击即可。）

| 接口 | 作用 |
|---|---|
| `GET  /api/status` | `{bridge, connected, name, addr, battery}` |
| `POST /api/send` | `{hex, timeout}` → `{payload:hex}` / `{timeout:true}` / `{error}` |
| `POST /api/connect` | 重新连（断了之后重试） |
| `POST /api/close` | 断开 |

静态页面也由它托管，所以是同源，不用管 CORS。

**网页这边的行为**：打开页面先 `GET /api/status`；探测到桥就把状态直接切成
「本地桥 · IINE_mouse」，自动读 `get_info` + 电量 + 五张表 —— 不需要点任何按钮。
探测不到（比如用 `python -m http.server` 起的纯静态站）就退回 Web Bluetooth，
那也会有「扫不到 → 列出全部设备」的兜底提示。

**已实测**：`ig05 / 0x1000 / 53% / 键盘 17 条 / 手柄键 0 条 / 鼠标 8 条 / 媒体键 8 条`，
鼠标栏读出来的方向是初始化后的正确值（上移 / 下移 / 左移 / 右移）。

**注意**：桥进程持有唯一的 GATT 连接，所以桥开着的时候 `v1_write.py` 之类的脚本
会连不上（报「没找到 AE41/AE42」），先关桥再跑脚本。

## 14. 设备模式、广播名与地址（2026-10-30 实测）

手柄切模式后，**传输方式、广播名、地址全都会变**，写死任何一项都必然失效。

| 模式 | 传输 | 扫描看到的名字 | 地址 | AE40 私有通道 |
|---|---|---|---|---|
| 私有 / 配置 | BLE | `IG05 Gamepad(BLE)` | 随机地址，如 `47:11:7B:FE:2C:3A` | ✅ 可用 |
| 鼠标 | BLE | `IINE_mouse` | `F8:B4:9A:CC:71:CE`（静态） | ✅ 可用 |
| 键盘 | BLE | `IINE-Keyboard` | 同上 | ✅ 可用 |
| Switch（主机） | **经典蓝牙 HID** | Windows 里显示 `Pro Controller`（`BTHENUM\DEV_0C857D0E25C8`） | `0C:85:7D:0E:25:C8` | ⚠️ 见下 |

### 关键坑：配好之后不再广播名字

手柄在私有模式下**一旦被连过一次**，BLE 广播里的 `name` 会变成 `None`：
扫描能扫到地址，但名字是空的。这时：

- 按名字匹配 → 直接漏掉（`d.name` 是 `None`，`in` 判断会抛/不命中）
- 按地址连 → **仍然正常**，AE40/AE41/AE42 都在，电量也能读

所以设备发现必须是三级：

```
显式 --addr  >  上次成功地址（.bridge_addr 缓存，不扫描）  >  扫描（先名字、再对无名设备探 AE40）  >  出厂默认
```

`bridge.py` 已按这个实现了，实测能在「无名广播」状态下自动找回手柄。

### Switch 模式下能不能改键

在 Switch 主机上它是标准 `Pro Controller`（经典蓝牙 HID），BLE 私有通道**同时**还开着，
但不再广播名字。只要知道地址（或从缓存里拿），仍然能连上去读 / 写五张表。
换句话说：**改键在哪种模式下都能做，只是找设备的方式不同。**

### 本次实测数据（私有模式，2026-10-30 18:2x）

```
get_info   ig05 / 0x1000
get_kb     17 条（出厂）
get_gp     17 条 —— 不再是空表
           16→18  17→19  18→17  19→16   ← 正是「竖着拿·键在下」那一档
get_mouse  8 条（16=左移 x-2 / 17=右移 x+2 / 18=下移 y+2 / 19=上移 y-2）
get_cs     8 条
get_sleep  discon=5  con=3
电量       85%
```

`get_gp` 从「空表」变成「17 条」这件事说明：**表一旦被写过就会一直存在**，
而 `set_restore`（初始化手柄）会把它清回空表。所以「手柄键读不出来」= 没写过 / 被初始化过，
不是读失败 —— 空表在协议层就是合法的 `0x90`（fixarray 长度 0）。
